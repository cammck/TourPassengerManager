# Tour Passenger Manager (SwiftUI)

A native iPhone app for managing passenger rosters across multiple tours: create a tour, import its passenger list from CSV, view/search/edit passengers, and export an updated roster — all stored locally on the device.

## Features

- **Face ID / passcode protection for passenger data** — the Tours home screen, creating tours, editing tour details/dates, and managing SMS templates all work without authenticating. The moment you tap into a tour to see its actual passenger roster, you're prompted for Face ID (or Touch ID, or the device passcode as a fallback). Nothing about any passenger — name, contact info, dietary or medical details — is visible before that succeeds.
  - Authentication is session-based: once unlocked, it stays unlocked while the app is in the foreground (no re-prompt every time you switch tours), and automatically re-locks the moment the app is backgrounded. Backgrounding and returning (e.g. to check a detail in another app) never discards in-progress work — if you're mid-edit on the SMS compose screen when the app locks, that screen stays open with your edits intact; the lock screen only appears once you back out to the passenger list itself
  - There's also a manual **Lock Passenger Details** option (in the filter/group menu inside a tour) if you want to re-lock without backgrounding the app — e.g. handing the phone to someone else briefly.
  - **Requires a one-time Xcode setup step** — see "Face ID setup" under *How to build it* below. Skipping it will crash the app the first time Face ID is triggered.
- **Multiple tours** — the home screen lists tours, split into two sections: **Current & Upcoming** (the tour running today, if any, pinned at the very top with a green "CURRENT" badge, followed by future tours soonest-first, then any undated tours) and **Past** (tours that have ended, most recently finished first). Each tour has its own **Tour Code** (e.g. a booking/departure code — this is the primary way tours are identified in the list, shown prominently), optional date range (which also determines current/upcoming/past placement), and a completely separate passenger roster. The tour *product* name (e.g. "Red Centre Explorer Tour") is set once, globally, in Settings — since it's the same across every departure, only the code and dates distinguish one tour from another. Create as many tours as you need, delete old ones with a swipe.
  - **New Tour Code and start date are pre-filled automatically**, based on the most recently scheduled existing tour: the code is suggested by incrementing its trailing number (e.g. `RCE2609` → `RCE2610`; a footer note explains where the suggestion came from), and the start date is predicted from a fixed weekly departure pattern — a tour ending on a **Monday** starts the next one the following **Thursday** (+3 days), ending **Thursday** starts the next **Sunday** (+3 days), and ending **Sunday** starts the next **Monday** (+1 day). Both are fully editable before saving; if the previous tour's end date doesn't fall on one of those three days, or there's no previous tour with dates at all, the date is left for manual entry rather than guessed incorrectly
- **CSV import per tour** via the Files app / iCloud Drive / Dropbox, etc. (`.fileImporter`)
  - Matches your manifest header exactly: `Surname, Firstname, Preferred Name, Combined Name, Yayes Lunch, Dietary Requirements, Manifest Medical Condition, Home Number, Mobile Number, Address, Email, Emergency Contact Name, Emergency Contact Number, Booking Number, JBR Booking Number, Room Type, Explorer Pack, Pickup Details, Pickup Flight Number, Pickup Flight Origin, Dropoff Details, Dropoff Flight Number, Dropoff Flight Destination, Weight`
  - **Pickup Details and Dropoff Details are automatically split** into separate location and time fields on import (e.g. "Downtown Hotel 7:30am" → location "Downtown Hotel", time "7:30am"). Recognizes times like `7:30am`, `7:30 AM`, `07:30` (24-hour), and `7am`. These are stored as `pickupLocation`/`pickupTime`/`dropoffLocation`/`dropoffTime` on each passenger, editable separately in the passenger detail screen, and recombined automatically for CSV export
  - **Pickup/Dropoff Flight Number and Origin/Destination** — only populated when a pickup or dropoff involves a flight; left blank for hotel/other ground transfers. Fully optional columns, editable per-passenger in the detail screen
  - Required: `Surname` (or `Combined Name`) — everything else is optional
  - Choose to **merge** (skip duplicate names) or **replace** that tour's roster
- **Search** within a tour by name, email, mobile number, booking number, or room type
- **Send SMS to selected passengers using templates**:
  - Tap the message icon (top right, inside a tour) to enter select mode, tap passengers to select them (or "Select All" — this respects whatever grouping/search is currently active, e.g. select everyone in the "Vegetarian" dietary group)
  - Choose a saved template or write a custom message
  - All selected passengers receive **one combined group text** — their names are merged into a natural list (e.g. "Hi Jane and John, ...") and shared details like a common pickup location appear once rather than repeating
  - Templates support placeholders that are filled in automatically: `{FirstName}, {Surname}, {PreferredName}, {CombinedName}, {MobileNumber}, {PickupDetails}, {DropoffDetails}, {PickupLocation}, {PickupTime}, {DropoffLocation}, {DropoffTime}, {PickupFlightNumber}, {PickupFlightOrigin}, {DropoffFlightNumber}, {DropoffFlightDestination}, {BookingNumber}, {RoomType}, {TourName}, {TourCode}, {DietaryRequirements}, {MedicalCondition}`
  - Comes with five real-world starter templates (Airport Pickup + Town Tour, Airport Pickup + Tali Dinner, We Pick Up from Airport, At Crowne Plaza + Town Tour, Caravan Park Pick Up) — these lean on manual per-send fill-ins (exact meeting time, allergy specifics) marked with `***`/`****`, so **the resolved message is editable right before you send** — the Send screen shows the fully token-resolved text in an editable box with a "Reset" button to discard your edits and start over from the template
  - Also available: `{TourDirectorFirstName}`, `{TourDirectorPreferredName}`, `{TourDirectorSurname}`, and the combined `{TourDirectorName}` — configured once, globally, in **Settings** (gear icon on the Tours home screen) and usable across every tour and template
  - `{TourName}` is also configured globally in **Settings**, alongside the Tour Director fields — it's the tour product's name (e.g. "Red Centre Explorer Tour"), constant across every departure. `{TourCode}` is the opposite: set per-tour (via **Tour Details**, the info icon inside a tour), since that's what actually distinguishes one tour from the next
  - Also available: `{TownTourTime}` — a **per-tour** parameter (unlike the Tour Director fields above, this is set separately for each tour). Set it when creating a tour, or anytime afterward via the **info icon** inside a tour. This is one of what will likely be several per-tour parameters; adding more later just needs a new field on `Tour`, a row in `TourDetailsView`, and an entry in `MessagePlaceholders`
  - Also available: `{DayXFullDate}` (e.g. "Sunday 23rd August") and `{DayXName}` (e.g. "Sunday"), where X is any day number of the tour — `{Day1FullDate}` is the tour's start date, `{Day2FullDate}` is the day after, and so on. These only resolve if the tour has a start date set (optional when creating a tour); if it doesn't, the tokens are left as-is so it's obvious a date is needed
  - **Time offsets**: `{PickupTime}`, `{DropoffTime}`, and `{TownTourTime}` accept an optional `+`/`-` duration, e.g. `{PickupTime + 15m}`, `{DropoffTime - 1h}`, `{TownTourTime + 1h30m}` — useful for things like "meet 15 minutes before the flight lands." Durations accept `h`/`hr`/`hrs`/`hours` and `m`/`min`/`mins`/`minutes`, matching is case-insensitive, and the result keeps the same 12-hour (am/pm) or 24-hour style as the original value, rolling over midnight/noon correctly. If a time can't be parsed (e.g. it's blank), the original value is left unchanged rather than breaking the message
  - **Conditional blocks**: wrap text in `{#Token}...{/Token}` and it only appears if `{Token}` would resolve to something non-blank for the passengers selected — e.g. `{#DietaryRequirements}Dietary requirements noted: {DietaryRequirements}. {/DietaryRequirements}` disappears entirely if nobody selected has a dietary requirement on file, rather than leaving an awkward "Dietary requirements noted: ." Works with any token, not just dietary — same idea applies to `{#MedicalCondition}`, `{#PickupFlightNumber}`, etc. The template editor has tap-to-insert buttons for the dietary and medical examples under "Tap to Insert a Conditional Snippet"
  - **Booking loops**: wrap text in `{#EachBooking}...{/EachBooking}` and it repeats once for each distinct booking among the selected passengers, instead of merging everyone's details into one combined sentence — e.g. `{#EachBooking}{CombinedName}: flight {PickupFlightNumber}, pickup {PickupTime} from {PickupLocation}.\n{/EachBooking}` gives guests on different flights their own line each. A booking is a shared literal Booking Number, or several Booking Numbers joined by a Booking Link (see Tour Details → Booking Links) — the same grouping the roster itself uses to cluster and delineate bookings — so a linked family group still gets one combined line rather than one per person. Passengers with no booking number (crew) aren't part of any booking and are skipped by the loop. Everything inside the block — plain tokens, time offsets, nested `{#Token}` conditional blocks, even `{Snippet:Name}` — resolves scoped to just that one booking's passengers, reusing the exact same resolution logic as the rest of the message. The template editor has a tap-to-insert example under "Tap to Insert a Booking Loop"
  - **Snippets**: a separate, lighter-weight kind of saved text — managed in their own section below Templates on the Message Templates screen — for reusable building blocks like a shared intro or signoff. A snippet is included inside a template with `{Snippet:Name}`, resolved before anything else, so tokens and conditional blocks inside the included snippet work normally as part of the combined message. Unlike templates, **snippets are never selectable directly on the Send SMS screen** — they only exist to be spliced into templates. Comes with two starter snippets, **Intro** and **Signoff**, and the five real starter templates already reference them via `{Snippet:Intro}` / `{Snippet:Signoff}` instead of repeating (and having to keep in sync) the same opening/closing lines five times over. Guards against circular references (two snippets including each other) and caps recursion depth, so a mistake can't hang or crash — an unresolvable or looping reference is just silently removed rather than breaking the message. The template editor lists all saved snippets as tap-to-insert buttons under "Tap to Include a Snippet"
  - **Fixed-number templates**: a template can be set to always send to a hardcoded number (or comma-separated numbers) instead of the selected passengers' own numbers — set this in the template editor via "Send to a fixed number instead." Useful for a template that notifies a driver or the office about a pickup rather than messaging the guest directly; placeholders still resolve using whichever passengers are selected when you send, even ones with no mobile number on file, since the message isn't going to their phone. These templates are marked with a 📌 in the Send SMS template picker and a "Fixed Number" badge on the Message Templates screen, and the Send screen's Recipients section shows the fixed number(s) instead of the usual passenger/mobile-number summary
  - Manage templates from the message-bubble icon on the Tours home screen (add/edit/delete; comes with four starter templates)
  - **Important — this is a group text, not private individual messages**: every recipient can see the other recipients' phone numbers and any replies in the thread, just like a normal group iMessage/SMS. If passengers shouldn't see each other's numbers, select and message them one at a time instead.
  - **Important platform limitation**: iOS does not allow any app to send text messages silently — Apple requires the person to review and tap Send themselves in the native Messages compose screen, as an anti-spam/anti-abuse measure. This app resolves the combined message and presents Apple's Messages composer pre-filled and addressed to everyone selected; you tap Send once to send to the whole group.
  - Sending SMS only works on a physical iPhone signed into Messages — the iOS Simulator cannot send text messages at all
- **Group the roster view** (tap the filter icon, top left) by:
  - All Passengers (default, alphabetical)
  - Pickup location
  - Dropoff location
  - Dietary Requirements (only passengers with one on file, grouped by requirement)
  - Medical Conditions (only passengers with one on file, grouped by condition)
  - **Every one of these views clusters passengers by booking number** (see "Related bookings" below) — there's no separate "By Booking Number" mode, because booking grouping applies everywhere at once, with a thin colored bar delineating one booking from the next
- **Related bookings** — from a passenger's detail screen, in Edit mode, link their Booking Number to one or more other booking numbers (pick from existing ones in the tour, or type a new one). Once linked, in **every view above**:
  - Passengers sharing a booking (or linked bookings) are always kept adjacent — positioned at the alphabetically-earliest name in the group, even inside a pickup-location or dietary-requirement group
  - A thin **colored accent bar** appears on the leading edge of each row — everyone in the same booking (or linked-booking group) shares a color, and the color changes for the next booking, so bookings are visually distinguishable without extra vertical space
  - A small purple link icon appears next to a passenger's name whenever their booking is linked to another
  - Links are transitive (linking A↔B and B↔C treats all three as one group) and per-tour (stored on the tour, not tied to the CSV/manifest data, so they don't affect CSV export)
- **Full detail/edit view**, organized into Name, Contact, Emergency Contact, Booking & Logistics, Related Bookings, and Catering & Welfare sections
- **Swipe left/right** on a passenger's detail screen to page through to the next/previous passenger, without going back to the list first. Built on SwiftUI's native `TabView(.page)` paging container, so adjacent passengers' cards are genuinely already laid out and visible peeking in from the screen edges as you drag — not just an animation that starts after you let go. Order matches whatever's currently on screen — if you're viewing "All Passengers," it follows that order (including booking clusters); if you're inside a grouped view (e.g. a specific pickup location), it pages through that filtered/grouped list. A bottom toolbar also shows Previous/Next buttons and a "3 of 24" position indicator as a visible, discoverable alternative to swiping — these page the same way, just without needing a drag. Since a right-swipe would otherwise also trigger iOS's own edge-swipe-to-go-back gesture, the default back button (and its swipe gesture, which is tied to it in SwiftUI's `NavigationStack`) is replaced with a manual back button whenever there's more than one passenger to page between, so the two gestures don't fight over the same swipe. Edit mode is scoped to whichever passenger is currently showing — paging away from one always resets to read-only for whichever passenger you land on, rather than carrying edit mode along with you
- **Ad hoc calling, texting, and emailing** — outside a tour's view (not editing), tapping any phone number field (**Mobile**, **Home Number**, or **Emergency Contact Number**) offers Call or Message, and tapping **Email** opens Mail addressed to them. No templates involved — this is just quick one-off contact, separate from the bulk SMS-with-templates flow described below
- **Email all passengers on a tour at once** — from the filter-icon menu inside a tour, "Email All Passengers" opens a single email addressed to every passenger with an email on file, with duplicates removed. Everyone goes in **Bcc**, not To/Cc, so passengers on the same tour never see each other's email address — the same convention any normal bulk email to a group would follow. Uses a `mailto:` link (opened via `UIApplication.shared.open(_:)`), pre-filled with the Tour Code as the subject — no template involved, same as the ad hoc single-passenger contact above. Deliberately **not** built with `MFMailComposeViewController` (the framework used for SMS elsewhere in the app): that class is hard-coded to always use Apple's built-in Mail app regardless of what's set as the default mail client in iOS Settings, while a `mailto:` link correctly opens whatever the person actually has set as default (Outlook, Gmail, etc.)
- **Multiple group photos** — a tour can have up to 3 group photos (`Tour.maxGroupPhotos`), for full coverage of a large group across several shots. Add them from Tour Details, where each shows its own thumbnail, a "N of M faces tagged" summary, and a delete button; picking photos there offers all remaining slots at once via the system photo picker. In the passenger list header they sit side by side within the same ~75%-width band, tappable individually. The full-screen viewer is a horizontal pager (swipe or use the page dots) starting on the photo you tapped, with pinch-to-zoom, drag-to-pan and double-tap-to-zoom on each page independently. Photos are downscaled to at most 2560 px on the long edge and stored as JPEG files in `Documents/TourPhotos/` (not inside `tours.json`), and are deleted along with their tour. Like the roster itself, photos are only visible after Face ID/passcode — the full-screen viewer and Tour Details sheet close automatically if the app re-locks. The ⋯ menu (hide/show faces, add a missed face, rescan) applies to whichever photo is currently on screen
- **Face tagging** — when a group photo is added, Apple's Vision framework finds the faces in it (scanning the whole photo plus four overlapping tiles, so small faces in big groups are caught). In the full-screen viewer every face is outlined — orange until tagged, green once tagged. Tap a face to pick which passenger it is; the ⋯ menu lets you hide the outlines, add a face Vision missed (tap its centre), or rescan that photo. Each tagged passenger's face then appears as a small round thumbnail beside their name in the passenger list, on their own detail screen (a larger version at the top), and next to their name in cross-tour search results. A passenger can only be tagged to one face across the whole tour — even across several photos — so tagging them again (on any photo) moves the tag. Face boxes are stored per photo (`TourGroupPhoto.faces`) as fractions of that photo, so they travel with backups; thumbnails are cropped from the photo on demand and never stored. Deleting a passenger clears their tag, and replacing the roster from CSV carries tags across to passengers with the same name, across every photo. Everything runs on-device — no extra permissions are needed
- **By Pickup grouping considers pickup time, not just location** — grouping the roster "By Pickup" clusters passengers by pickup location *and* pickup time together, so (for example) two trains into the same station at different times become two separate groups instead of one merged group, titled e.g. "Alice Springs Train Station · 10:30 AM". A location with no time set gets its own group titled with just the location. Within a location, groups are ordered chronologically by time where it can be parsed (plain formats like "2:00 PM" or "14:00"); free-text times that can't be parsed ("TBC", "Morning") sort alphabetically instead, after every parseable time
- **Crew** — anyone with no Booking Number and no JBR Booking Number is treated as crew (`Passenger.isCrew`). They get a **CREW** badge, are listed after all the passengers (in their own **Crew** section in the All Passengers view, and at the bottom of each group in the other groupings), and are counted separately ("42 passengers · 3 crew"). They're still fully available for tagging in the group photo. Giving someone a booking number moves them back into the passengers
- **Add passengers manually** for last-minute additions
- **Delete passengers** via swipe or from the detail screen
- **Passenger Map** — from the filter-icon menu inside a tour, "Passenger Map" shows where the tour's passengers are coming from: one pin per distinct home address, geocoded from the Address field via Apple's geocoding service (no extra permission needed — it's a plain address-to-coordinate lookup, not anything involving the device's own location). Passengers who share an address are combined onto a single pin rather than stacking separate pins — tap a pin to see everyone there, combined under their first and last names (e.g. "Jane Smith and John Smith"), each with their mobile number if on file. A banner lists anyone not shown on the map — no address on file, or an address that couldn't be located — so it's clear the map isn't silently missing people; crew are excluded from the map entirely (they never have a home address on file) and from that count, so they don't show up as misleadingly "not shown." Geocoded addresses are cached to disk (`GeocodeCache`, keyed by a normalized form of the address) so the same address is only ever looked up once, even across tours and app launches; addresses are looked up one at a time rather than all at once, in line with Apple's guidance for its geocoding service. Two passengers who typed the same address slightly differently (e.g. "25 King St" vs "25 King Street") still combine onto one pin: normalization expands common street-type abbreviations to a shared canonical form (`GeocodeCache.streetTypeAbbreviations`), and as a second line of defense, any pins that still geocode within ~50m of each other are merged after the fact. Like the rest of the passenger roster, this map closes automatically if the app re-locks. Navigation works both ways: tapping a passenger in a pin's detail sheet pushes into their full detail screen (paging through just that address's household, not the whole tour), and tapping a passenger's Address field on their own detail screen opens the map zoomed in on their own pin with that pin's detail sheet already showing
- Both maps use MapKit's modern `Map(position:)`/`Annotation` API (iOS 17+) rather than the older `Map(coordinateRegion:annotationItems:)`/`MapAnnotation`, which is known to become unstable with larger numbers of custom annotations — the All Passengers map in particular can easily combine 50+ pins across every tour
- **All Passengers map** — the map icon on the Tours screen's toolbar opens a second map combining passengers from *every* tour (`AllPassengersMapView`), for spotting repeat travelers or family across different departures. It never geocodes anything itself — it only reads addresses already looked up by opening a tour's own Passenger Map, so it opens instantly regardless of how many tours exist, at the cost of a tour whose own map has never been opened simply not appearing here yet (a banner shows how many passengers are currently shown (crew excluded, same as the per-tour map)). Pins combine the same way as the per-tour map, across tours as well as within one. Tapping a passenger pushes into their own tour's detail screen, paging through that tour's full roster, with a small tour-code badge next to each name since the same address can span different tours. Like global search and backup export/import, this view surfaces passenger data across every tour from the Tours screen, which isn't itself behind Face ID — so it goes through the same unlock gate those do before opening
- **Export CSV** of a tour's current roster (same column layout, plus Staff Notes) via the system share sheet
- **Local persistence** — all tours and their rosters are saved to a JSON file in the app's Documents directory, so everything survives app relaunches (no account or internet required)
- **Full backup export/import**, to move everything to another device or keep a safety copy — from the external-drive icon on the Tours home screen:
  - **Export Backup** bundles every tour (with its passengers, booking links, notes, and group photo), every SMS template and snippet, and your Settings (Tour Director, Tour Name) into a single JSON file, then opens the system share sheet (AirDrop, Files, Mail, etc.) to send it wherever you like
  - **Import Backup** reads a backup file back in, with a choice of **Replace existing data** (wipes everything currently in the app and restores exactly what's in the file — asks for confirmation first, since it can't be undone) or **Merge** (adds new tours/templates/snippets, or updates the matching ones already present by their internal ID, so re-importing the same file twice is safe; your current Settings are left alone in this mode)
  - **Both export and import require Face ID/Touch ID/passcode first**, the same as opening any individual tour — a backup contains every passenger's details across every tour, so it needs the same protection as viewing one tour's roster; otherwise it would be a way to get at that data from the Tours list without ever authenticating
- **Search across every tour at once**, not just within one — the magnifying-glass icon on the Tours home screen opens a dedicated search screen matching by name, email, mobile number, booking number, or room type across every passenger in every tour. Each result shows which tour it belongs to (a colored code badge next to the name), and tapping one goes straight to that passenger's detail screen, where you can still swipe to page through the rest of that tour's roster. Like backup export/import, this **requires Face ID/Touch ID/passcode first**, since results surface passenger details from every tour at once — the same protection as opening any individual tour, applied here because this is another way to reach that data from the (unprotected) Tours list

There is intentionally no check-in/attendance tracking — the app is purely for managing roster data.

## How to build it

You'll need a Mac with **Xcode 15 or later** (free from the Mac App Store). The Passenger Map and All Passengers map use MapKit's newer `Map(position:)` API, which needs an **iOS 17+** deployment target and device/simulator — the rest of the app has no such requirement.

1. Open Xcode → **File → New → Project…**
2. Choose **iOS → App**, click Next.
3. Product Name: `TourPassengerManager`. Interface: **SwiftUI**. Language: **Swift**. Uncheck "Use Core Data" and "Include Tests" (not needed).
4. Save it anywhere on your Mac.
5. Xcode will have created a default `TourPassengerManagerApp.swift` and `ContentView.swift` — **delete `ContentView.swift`** (move to trash), and **replace** the generated `TourPassengerManagerApp.swift` with the one provided here.
6. In Xcode's Project Navigator, right-click your app's group/folder → **New Group** and create `Models`, `Services`, and `Views` groups to mirror the structure above.
7. Drag the corresponding `.swift` files from this download into each group (check **"Copy items if needed"** and make sure the app target's checkbox is ticked in the dialog).
8. Select your project in the navigator → your target → **Signing & Capabilities** → choose your Apple ID under **Team** (a free Apple ID works for running on your own device; you'll just need to trust the developer profile on the iPhone under Settings → General → VPN & Device Management the first time).
9. **Face ID setup (required, or the app will crash on first use of Face ID)**: select your target → the **Info** tab → hover over any row in "Custom iOS Target Properties" and click the **+** that appears → type `Privacy - Face ID Usage Description` as the key (Xcode will autocomplete it to `NSFaceIDUsageDescription`) → set its value/type to **String** → enter something like `Face ID is used to protect passenger details.` as the value. iOS requires this string and will terminate the app immediately if it's missing and Face ID is triggered — Touch ID/passcode fallback don't need it, but Face ID specifically does.
10. Plug in your iPhone (or use a Simulator), select it as the run destination in the toolbar, and press **⌘R** to build and run.

Note: the iOS **Simulator** doesn't have real Face ID hardware, but it does simulate it — with the Simulator running, use its menu **Features → Face ID → Enrolled**, then **Features → Face ID → Matching Face** to simulate a successful unlock when the app prompts (or **Non-matching Face** to test a failure). On a real device it uses your actual enrolled Face ID/Touch ID/passcode as normal.

That's it — no external dependencies or CocoaPods/SPM packages required, everything uses stock SwiftUI/UIKit/MessageUI APIs. `MessageUI` is a standard system framework; `import MessageUI` should work with no extra setup, but if Xcode ever complains about a missing framework, add it manually under your target → **General** → **Frameworks, Libraries, and Embedded Content** → **+** → search "MessageUI".

1. Launch the app — you'll land on the **Tours** screen. Tap **+** and give it a name (e.g. "Melbourne Highlights – Sept 2026").
2. Tap into the tour, then use the **import** button (top left, download-tray icon) to load `sample-passengers.csv` (included in this folder — copy it onto your iPhone first via AirDrop, Files app, or iCloud Drive), or add a few passengers manually with **+**.

## Notes on extending it

- **Sorting/grouping**: currently sorted alphabetically by name within a tour; easy to add sort-by-room or sort-by-booking-number in `PassengerListView`.
- **Storage**: uses a flat JSON file for simplicity, good for a handful of tours with tens of passengers each. If you ever need to scale up significantly or add multi-device sync, swapping in SwiftData or CloudKit would be the natural next step — `TourStore` is the only class that would need to change.
- **CSV column names**: if your CSV export uses different header names than the ones listed above, add more aliases to `Passenger.csvFieldAliases` in `Passenger.swift` — no other code needs to change.
- **Duplicating a tour**: if you run the same itinerary repeatedly, you could add a "Duplicate Tour" action in `ToursListView` that copies a `Tour` (with a new `id`) as a starting point for the next departure. Set `groupPhotos` to `[]` on the copy — deleting a tour removes its photo files, so two tours must never share one.
- **Group photo tuning**: the header's total width is `widthFraction` in `GroupPhotoHeaderView`; the photo limit is `Tour.maxGroupPhotos`; the stored photo's maximum size and JPEG quality are `maxStoredDimension` and `jpegQuality` in `TourPhotoStore`. Photos are included in backups (base64 inside the JSON), so lowering those keeps backup files smaller if you accumulate many tours with several photos each.
